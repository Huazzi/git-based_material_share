# Git-Based Material Share V2 架构 Review

## 一、Review 结论

当前
文件搜索
↓
上传 / 创建目录 / 删除
↓
PDF / DOCX / Markdown / 图片 / 视频 / 代码预览
↓
文件下载

```
因此，**V2 不应该继续以“增加功能”为第一目标。**

我的架构结论是：

> V1 的问题已经从“功能实现问题”转变为“职责边界、API 调用模型、安全模型和文件传输模型问题”。

我建议 V2 的核心目标定义为：

```text
1. GitHub First
2. Tree Snapshot Driven
3. Storage Provider Abstraction
4. Previewer Plugin Architecture
5. Serialized Mutation
6. Zero General-purpose Proxy
7. Security by Default
```

最终目标架构：

```text
┌──────────────────────────────────────────┐
│                 Vue UI                   │
│                                          │
│ FileBrowser  UploadDialog  PreviewModal  │
└────────────────────┬─────────────────────┘
                     │
              Application Layer
                     │
      ┌──────────────┼──────────────┐
      │              │              │
      ▼              ▼              ▼
 Repository       Upload         Preview
 Browser          Queue          Manager
      │              │              │
      └──────────────┼──────────────┘
                     │
            StorageProvider
                     │
                     ▼
          GitHubStorageProvider
                     │
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
   Git Trees     Contents API   Git Data API
   Read/Search   Raw Content    Atomic Mutation
```

**总体建议：进行 V2 重构，不建议推倒产品重写。**

# 二、现有架构问题清单

## P0-01：Markdown / DOCX 预览与 PAT 存储形成潜在 XSS 攻击链

这是我认为当前最高优先级的问题。

当前配置直接执行：

```javascript
localStorage.setItem(
    'learningSiteConfig',
    JSON.stringify(config)
);
```

而 `config` 包含 PAT

Markdown：

```javascript
previewContent.value = marked.parse(processedContent);
```

DOCX：

```javascript
const result = await mammoth.convertToHtml({
    arrayBuffer: docxResponse.data
});

previewContent.value = result.value;
```

页面又直接：

```html
<div
    v-else-if="previewType === 'docx'"
    v-html="previewContent">
</div>

<div
    v-else-if="previewType === 'markdown'"
    v-html="previewContent">
</div>
```

当前代码链路可以直接从仓库文档生成 HTML，再通过 `v-html` 插入 DOM

Marked 官方明确说明其输出 HTML **不会自动进行 sanitization**；Mammoth 同样明确声明不会清理源文档，并特别警告 DOCX 中的恶意链接在 HTML 嵌入场景可能执行 JavaScript

因此我认为存在这样的潜在攻击链：

```text
恶意 Markdown / DOCX
        ↓
marked / mammoth
        ↓
HTML
        ↓
v-html
        ↓
XSS
        ↓
localStorage
        ↓
PAT
```

### V2 方案

引入：

```text
DOMPurify
```

统一执行：

```javascript
const html = marked.parse(markdown);

const safeHtml = DOMPurify.sanitize(html);
```

DOCX：

```javascript
const result = await mammoth.convertToHtml({
    arrayBuffer
});

const safeHtml = DOMPurify.sanitize(result.value);
```

更重要的是：

```text
Repository Config
        ↓
localStorage

PAT
        ↓
sessionStorage
```

默认关闭 PAT 持久化。

可以提供：

```text
☐ 在此设备记住访问令牌
```

只有用户主动勾选才进入 `localStorage`。

GitHub 官方当前也建议 fine-grained PAT；它可以限制到特定 owner 和特定 repository，并授予细粒度权限

**严重度：P0**

## P0-02：Netlify Proxy 的文件传输模型存在根本性问题

当前 `proxy.js`：

```javascript
const response = await axios.get(url, {
    responseType: 'arraybuffer'
});

return {
    statusCode: 200,
    body: response.data.toString('base64'),
    isBase64Encoded: true
};
```

也就是：

```text
GitHub
   ↓
Netlify Function
   ↓
完整 ArrayBuffer
   ↓
Base64
   ↓
Netlify Response
   ↓
Browser
```

当前实现确实会完整缓冲并 Base64 返回文件

Netlify 当前 buffered synchronous Functions 的 request/response payload 上限为 6 MB；二进制 Base64 编码存在约 30% 额外开销，因此有效二进制大小约为 4.5 MB

但当前以下功能全部依赖 Proxy：

```text
下载
图片预览
PDF 预览
视频预览
DOCX 预览
```

相关调用直接散落在 `downloadFile()` 和 `openFilePreview()` 中

### 我的结论

`proxy.js` 应从 V2 删除。

V2 应统一通过 GitHub Contents API 的 raw media type 获取原始文件。

设计：

```javascript
async getRawContent(path) {
    return client.get(
        `/repos/${owner}/${repo}/contents/${path}`,
        {
            params: {
                ref: branch
            },
            headers: {
                Accept: 'application/vnd.github.raw+json'
            },
            responseType: 'arraybuffer'
        }
    );
}
```

GitHub 官方说明：

```text
<= 1 MB
Contents API 全功能支持

1 MB ～ 100 MB
raw / object media type

> 100 MB
Contents API 不支持
```

因此你的 V2 完全可以：

```text
Browser
   ↓
GitHub API
   ↓
ArrayBuffer / Blob
```

而不是：

```text
Browser
   ↓
Netlify
   ↓
GitHub
   ↓
Netlify
   ↓
Browser
```

**严重度：P0**

## P0-03：当前“删除文件夹”实际上存在逻辑 Bug

当前页面对文件和文件夹都显示删除按钮：

```html
<button
    @click.stop="showDeleteConfirm(item)"
    class="action-icon"
    title="删除">
```

但 `confirmDelete()` 无论类型都执行：

```javascript
const fileResponse = await axios.get(url, ...);

const sha = fileResponse.data.sha;

await axios.delete(url, {
    data: {
        sha
    }
});
```

问题是：

```text
GET /contents/file.txt
        ↓
Object
        ↓
data.sha

GET /contents/folder
        ↓
Array<File>
        ↓
data.sha === undefined
```

因此基于当前代码逻辑推断，目录删除无法按文件删除逻辑正确执行。

而且你创建目录采用：

```text
folder/
└── .gitkeep
```

### V2 方案

定义两个明确方法：

```javascript
deleteFile(path, sha)

deleteDirectory(path)
```

推荐 `deleteDirectory()` 使用 Git Data API。

流程：

```text
GET Branch Ref
      ↓
GET Current Commit
      ↓
GET Tree
      ↓
找到 path/ 下全部 Blob
      ↓
Create Tree
sha = null
      ↓
Create Commit
      ↓
Update Branch Ref
```

一次 commit 删除整个目录。

不要：

```text
DELETE file 1
commit

DELETE file 2
commit

DELETE file 3
commit
```

否则删除一个 100 文件目录将制造 100 个 commits。

**严重度：P0**

## P0-04：上传没有真实文件大小边界

当前上传直接：

```javascript
const base64Content =
    await encodeFileAsBase64(fileToUpload.value);
```

而 `encodeFileAsBase64()` 使用：

```javascript
reader.readAsDataURL(file);
```

实际内存链路近似：

```text
File
 ↓
FileReader
 ↓
Data URL String
 ↓
Base64 String
 ↓
JSON Payload
 ↓
Axios Request
```

例如：

```text
50 MiB File
     ↓
约 66.7 MiB Base64
     ↓
JS String / Request Body 等额外内存
```

这是基于 Base64 编码模型与当前实现做出的工程判断。

### V2 建议

默认：

```javascript
const MAX_UPLOAD_SIZE = 25 * 1024 * 1024;
```

高级设置：

```text
最大上传文件：

● 25 MiB 推荐
○ 50 MiB
```

超过直接阻止：

```text
此文件为 82.4 MiB。

GitHub Material Hub 默认只支持上传
25 MiB 以内文件。

建议使用其他存储服务保存大型文件。
```

不要把 GitHub 的 100 MB 边界直接当产品限制。

**严重度：P0**

# 三、P1 架构问题

## P1-01：目录浏览存在严重 N+1 API

当前：

```javascript
const response = await axios.get(contentsUrl);
```

然后：

```javascript
await Promise.all(
    response.data.map(async item => {
        await axios.get(commitsUrl, {
            params: {
                path: item.path,
                per_page: 1
            }
        });
    })
);
```

因此：

```text
10 Files
1 + 10 requests

100 Files
1 + 100 requests

500 Files
1 + 500 requests
```

GitHub REST API 当前最多允许 100 个并发 REST/GraphQL 请求，同时还存在 secondary rate limits

### V2 方案

**删除实时 lastModified 查询。**

改用：

```text
GET /repos/{owner}/{repo}/git/trees/{branch}?recursive=1
```

一次加载 Repository Tree。

GitHub 官方说明 recursive tree 最大：

```text
100,000 entries
或
7 MB response
```

对你的个人文件 Hub 来说远远足够。

加载：

```text
GitHub Tree
      ↓
RepositoryTreeCache
      ↓
list("Java/")
search("Spring")
get("Java/Spring.pdf")
```

全部前端计算。

## P1-02：搜索同样存在 N+1，而且只读取第一页

当前：

```javascript
GET /search/code
per_page: 100
```

然后对每个结果：

```javascript
GET /contents/{item.path}
```

最后：

```javascript
await Promise.all(fileDetailsPromises)
```

因此：

```text
Search API
   ↓
100 Results
   ↓
100 Contents API
```

并且代码没有 pagination。

所以搜索实际存在：

```text
最多处理第一页 100 条结果
+
N+1 API
```

GitHub 的搜索类 API 还有独立于 core REST API 的自定义 rate limit 分类

### V2

Repository Tree 已加载：

```javascript
function searchFiles(query) {
    const normalizedQuery =
        query.trim().toLowerCase();

    return tree.files.filter(file =>
        file.name
            .toLowerCase()
            .includes(normalizedQuery)
    );
}
```

搜索：

```text
0 GitHub API Request
```

这是 V2 最大的性能收益之一。

## P1-04：GitHub / Gitee 当前属于“伪抽象”

你目前：

```javascript
const apiBaseUrl = computed(() => {
    return config.platform === 'github'
        ? GITHUB_API_BASE
        : GITEE_API_BASE;
});
```

但 Header：

```javascript
Accept: 'application/vnd.github.v3+json'

Authorization: `token ${config.token}`
```

上传又需要：

```javascript
const method =
    config.platform === 'github'
        ? 'put'
        : 'post';
```

搜索：

```javascript
if (config.platform === 'github') {
    // GitHub Search API
} else {
    // recursiveSearch
}
```

这说明平台差异已经泄漏到业务层。

继续下去会变成：

```text
if github
else if gitee
else if gitlab
else if ...
```

### V2

定义：

```javascript
class StorageProvider {
    async initialize() {}

    async refresh() {}

    async list(path) {}

    async search(query) {}

    async getRaw(path) {}

    async upload(path, file, options) {}

    async deleteFile(path) {}

    async deleteDirectory(path) {}
}
```

然后：

```text
StorageProvider
      │
      ├── GitHubStorageProvider
      │
      ├── GiteeStorageProvider    Future
      │
      └── R2StorageProvider       Future
```

**我的建议是 V2 先只实现 GitHubStorageProvider。**

不要为了“看起来支持多平台”维护一个不完整抽象。

```text

## P2-03：上传进度是模拟数据

```javascript

### V2

```text
方案 A
不显示百分比
显示“正在上传...”

```text

更好。

# 九、GitHub Client 设计

我建议：

```javascript
export function createGitHubClient({
    token
}) {
    const client = axios.create({
        baseURL: 'https://api.github.com',
        headers: {
            Accept:
                'application/vnd.github+json',
            'X-GitHub-Api-Version':
                '2026-03-10'
        }
    });

    if (token) {
        client.defaults.headers.common.Authorization =
            `Bearer ${token}`;
    }

    return client;
}
```

GitHub 当前 REST API 最新版本为 `2026-03-10`，官方建议通过 `X-GitHub-Api-Version` 明确指定 API 版本；未提供该 header 时目前默认使用 `2022-11-28`

再增加 interceptor：

```text
Response
   ↓
RateLimitTracker

x-ratelimit-limit
x-ratelimit-remaining
x-ratelimit-reset
retry-after
```

页面状态栏：

```text

```

我认为这非常适合你的项目。

# 十、V2 不建议立即引入 `.material-index.json`

这里我要修正我上一次回答中的一个建议。

上一次我推荐：

```text
.material-index.json
```

但真正看完当前完整代码后，我现在认为：

> **V2 第一阶段不应该引入 metadata index。**

原因：

```text
upload file
     ↓
update index

delete file
     ↓
update index

rename
     ↓
update index
```

它会引入：

```text
双写一致性
```

问题。

例如：

```text
File Commit Success
Index Commit Failed
```

结果：

```text
Repository
!=
Material Index
```

对于你目前的规模：

```text
Git Tree Snapshot
```

更加简单。

GitHub 官方本身也建议递归获取仓库内容时使用 Git Trees API，而 Contents API 单个目录还存在 1,000 文件上限

因此：

### V2

```text
Git Tree
作为 Source of Truth
```

### V3

只有需要：

```text
收藏
标签
自定义备注
访问次数
最近上传
```

这些 Git Tree 无法表达的数据时，再引入：

```text
.material-share.json
```
